## A. 本次要改（后台 / 后端维护）

### A1 补五分化框架模板

**现状**
- 库里只有两条模板：`three-split-classic`（三分化框架）、`fixed-push-strength`（推日成品）。
- 五分化**没有模板**，`_derive_scene_tag` 里虽有 `days_per_week==5 → 五分化` 的派生规则，但没有 5 板块模板，筛选「五分化」永远是空的。

**目标**
- 新增一条 `five-split-classic`，`template_type="framework"`，`days_per_week=5`，5 个板块：
  胸 / 背 / 腿 / 肩 / 臂。
- 槽位角色与组次区间沿用三分化 seed 的结构（`main` / `assist` / `isolation`，热身组数照现有写法）。

**本期范围**
- 只预置三分化、五分化两条框架模板。
- 其他分化（二分化上下肢、四分化、PPL 等）**不预置**；后续由后台手动建成品或框架模板，例如「背部专项训练计划」这类单部位成品。

**涉及文件**
- `gym-coach/api/app/services/plan_seed.py`：新增五分化 seed；`_derive_scene_tag` 无需改。

### A2 配动作：冷门奥举 / 杂技动作被顶上来

**现象（实测三分化）**
- 腿日主项配出「杠铃上送抓举平衡」「杠铃肌肉抓举」这类奥林匹克举动作，不属于大众健身房常规训练。
- 主项应优先深蹲 / 硬拉 / 弓步蹲 / 腿举 / 卧推 / 划船这类常用器械动作。

**根因**
- `plan_service._resolve_exercise_row` 打分只看：目标肌群 +20、臂推拉细分 +15、器械不重复 +3、亚区不重复 +2、`coach_core` +1。
- 常用动作和冷门动作只差 1 分，没有常用度门槛，5632 条里的冷门动作会被顶上来。

**修法**
1. `coach_core`（280 条常用动作）作为优先池：`main` 主项优先从 core 挑；非 core 降权，不硬排除（伤病 / 器械受限时允许兜底）。
2. 检查 enriched JSON 的 `modality` / `category` / 器械标签，识别并过滤奥举、杂技、平衡类出界动作。
3. 回归抽样：三分化腿日主项必须是深蹲 / 硬拉 / 弓步蹲 / 腿举类，不允许抓举 / 翻举 / 挺举。

**涉及文件**
- `gym-coach/api/app/services/plan_service.py`：`_resolve_exercise_row`、`_retrieve_for_slot`、打分段（约 700–718 行）。

### A3 配动作：孤立槽位配空

**现象（实测三分化）**
- 胸 `isolation` 槽位返回「槽位·孤立 / 待补充」，没有候选动作。

**根因（待排查）**
- 检索池按 `target_muscle=胸` + `role=isolation` 没命中；可能是角色标签与检索角色对不上，或亚区过滤过严。

**修法**
1. 先在 `_retrieve_for_slot` 打印候选数量，确认是「没候选」还是「被过滤掉」。
2. 孤立槽位允许退到同肌群 `assist` 兜底，并在备注标注「孤立动作暂缺，已用辅助动作替代」。

**涉及文件**
- 同 A2，`plan_service.py`。

### A4 图床现状澄清（**不是缺依赖**）

**现状**
- `services/storage.py` 已实现双后端：`local`（默认）/ `s3`（R2 / OSS 等 S3 兼容）。
- 当前 `storage_backend = "local"`：上传落 `api/static/...`，返回 `/static/{key}` 相对路径。
- `/static/exercises`、`/static/plans`、`/static/studio` 已在 `main.py` 挂载；H5 `vite.config.ts` 已代理 `/static` 到 8000。

**澄清**
- 上传后拿到本地地址，**不是因为没装依赖**。`boto3` 只有切到 `storage_backend=s3` 时才需要；local 模式不需要任何额外依赖。
- 真正没做的事是：**没有把后端从 local 切到对象存储**。

**待决策（暂不做）**
- 是否接 R2 / OSS。要上时只需：
  1. `pip install boto3`
  2. `.env` 配：`STORAGE_BACKEND=s3`、`S3_ENDPOINT_URL`、`S3_BUCKET_NAME`、`S3_PUBLIC_BASE_URL`、`S3_ACCESS_KEY_ID`、`S3_SECRET_ACCESS_KEY`
  3. 代码不用改。
- 注意：`/static/...` 相对路径只在 H5 与 API 同域下成立；将来封装 App / 小程序前，必须先切对象存储。

## B. 暂不实现，仅记录的后台规划（后面再细聊实现思路）

### B1 内容资产线
动作库 / 素材库 / 内容工坊 / 计划模板。工坊交互终版见 `docs/设计稿/内容工坊-交互重构/`。

### B2 AI 体验线
- **Badcase 池**：H5 用户反馈的对话坏案例，按归因分流（意图识别 / 工具调用 / 回答质量 / 长对话）。
- **评测台**：H5 的 AI 能力评测——评测集、跑批、规则分 + 裁判模型分、版本对比。**不是**动作数据打分。
- **设置**：LLM 配置、Prompt 版本管理。

### B3 Token / 成本监测
- 独立记 `llm_usage_log`（场景 / 模型 / 输入输出 tokens / 时间）；价格表单独一张 `llm_model_price`，价格不写死在代码里；按场景聚合成本。上线后再接。

### B4 前后端分层（不拆仓）
- 现状：接口都挂在 H5 项目里。后面补路由前缀 `/h5/*`、`/admin/*`，分层服务；共用一层服务，先不拆仓库。
- 隐患：`database_url = sqlite:///./data/gym.db` 是相对 CWD，启动目录不同会连错库；需改成基于 settings 的绝对路径。

### B5 分化类型设计约定
- 代码里**不要**把三 / 四 / 五分化做成枚举；只存 `days_per_week + 板块部位集合`，标签由 `_derive_scene_tag` 派生。后续新增分化不用改代码。
